# Building My Two-Site K3s Homelab — *GitOps, Tailscale & Monitoring* 🚀

Over the last few days I’ve been building a small Kubernetes homelab.

The idea was simple: I wanted something small enough that I can understand every part of it, but still realistic enough to learn things I can use elsewhere.

I ended up with **two separate K3s clusters**:

- one at home on a **Radxa X4**
- one on an ARM cloud VM

They are connected with **Tailscale**, managed through **Flux GitOps**, and monitored with **Zabbix and Grafana**.

The lab is still a work in progress, but the core setup is now stable enough to write about.

---

## 🧭 Current Architecture

The setup currently looks roughly like this:

```text
                        GitHub
                           |
                           | Flux GitOps
                +----------+----------+
                |                     |
                v                     v
             Home site             Cloud site
             K3s cluster           K3s cluster
                |                     |
                +------ Tailscale ----+
                                      |
                        +-------------+-------------+
                        |                           |
                     Zabbix                      Grafana
                        |
                 Cross-site monitoring

                ^
                |
        CachyOS workstation
```

My main management workstation is now **CachyOS**.

From there I manage both clusters with:

- `kubectl`
- Helm
- Flux
- SOPS
- age
- Git
- SSH
- Tailscale

## 🤔 Why Two Clusters?

At first I considered connecting both machines into one Kubernetes cluster over Tailscale.

Technically it can be done.

I decided not to.

The problem is not Kubernetes itself, but the control plane and especially **etcd**. Stretching etcd over a WAN link adds latency and another failure point for no real benefit in my setup.

So instead I kept them independent:

```text
Home cluster
  └── independent etcd

Cloud cluster
  └── independent etcd
```

If the home internet goes down, the Radxa can continue working locally.

If the Radxa dies, the cloud cluster keeps running.

That separation also makes the cloud cluster useful as an external monitoring and future backup location.

## 🔄 GitOps with Flux

Both clusters are managed with **Flux**.

The repository is split so each cluster reconciles only its own path:

```text
clusters/
├── home-cluster/
│   ├── flux-system/
│   └── infrastructure/
│
└── cloud-cluster/
    ├── flux-system/
    ├── infrastructure/
    └── monitoring/
        ├── grafana/
        └── zabbix/
```

The basic flow is:

```text
Git change
   |
   v
GitHub
   |
   v
Flux
   |
   v
Kubernetes
```

So if I change a manifest and push it to GitHub, Flux detects it and applies it to the correct cluster.

I also added GitHub Actions validation so obvious YAML and manifest problems can be caught before they reach the clusters.

## 🔐 Secrets with SOPS + age

Plaintext secrets in Git were a no-go from the beginning.

For this I use:

- **SOPS**
- **age**

Each cluster has its own age key pair.

Encrypted files can safely stay in the repository while the private keys remain outside Git.

Examples include:

- DNS provider API tokens
- Grafana admin credentials
- PostgreSQL credentials

Typical encrypted files look like:

```text
dns-api-token.sops.yaml
admin-secret.sops.yaml
postgres-access.sops.yaml
```

Flux decrypts them inside the cluster during reconciliation.

Tailscale is doing a lot of the boring networking work for me.

It connects:

```text
management workstation
home node
cloud node
```

That gives me private access between all systems without exposing SSH directly to the internet.

The same Tailscale network is also used for monitoring traffic between the home and cloud environments.

## 🔒 DNS and TLS

The lab uses a domain managed through Cloudflare DNS.

Kubernetes services live under a dedicated lab subdomain, with certificates handled automatically by:

- cert-manager
- Let's Encrypt
- Cloudflare DNS-01

Traefik handles ingress inside Kubernetes.

This means I can use normal HTTPS endpoints without manually renewing certificates.

## 📊 Monitoring with Zabbix and Grafana

Monitoring runs in the cloud cluster.

That was intentional.

If Zabbix and Grafana lived only on the Radxa, they would disappear at exactly the same time as the home cluster if something went wrong.

Instead:

```text
home node
   |
   | Tailscale
   v
Zabbix
   |
   v
Grafana
```

Zabbix currently monitors both hosts.

Collected data includes:

- CPU usage
- memory
- filesystem usage
- network traffic
- system uptime
- agent health

Grafana then uses Zabbix as a data source for a single dashboard covering both machines.

## 💾 Swapping the Radxa SSD

One of the more interesting side jobs was replacing the Radxa SSD.

Originally I used a **1 TB Crucial NVMe**.

That was complete overkill.

The actual Debian + K3s setup was only using a few gigabytes, so I decided to move it to a **512 GB NVMe** and reuse the 1 TB drive in my main PC.

Because the destination disk was smaller than the source, I did not want to do a raw block clone.

Instead I created the new layout manually:

```text
EFI
/boot
LVM
├── root
├── k3s
└── backup
```

Then copied the filesystems with `rsync`.

The data copy itself was easy.

The fun started on first boot. 😄

The Radxa dropped directly into:

```text
grub>
```

GRUB was there, but the EFI-side GRUB config still referenced the old `/boot` UUID.

Manually setting the correct boot partition worked:

```text
set root=(hd0,gpt2)
set prefix=(hd0,gpt2)/grub
insmod normal
normal
```

Debian booted.

After that I corrected the EFI GRUB config so it searched for the UUID of the new `/boot` filesystem.

Once that was fixed, the system booted normally again.

K3s came back up, the node returned to `Ready`, and all the workloads recovered.

The old 1 TB SSD was then wiped and reformatted as Btrfs for reuse.

That part of the project probably deserves its own separate post because migrating Linux + LVM + K3s to a smaller disk turned out to be more interesting than expected.

## 🖥️ Moving the Management Workstation to CachyOS

The lab was originally managed from Windows.

That worked fine, but once most of the environment became Linux-based, it made more sense to move the management side to CachyOS as well.

I migrated:

- kubeconfig
- SSH keys
- SOPS age keys
- Git configuration
- the homelab repository

Then installed the native Linux tooling:

```text

helm
flux
sops
age
tailscale
```

Both clusters are now reachable from the same workstation:

```bash
kubectl --context home-cluster get nodes
kubectl --context cloud-cluster get nodes
```

GitHub access also moved to SSH.

This gives me one Linux workstation for both normal desktop use and infrastructure management.

## 🧪 Things That Went Wrong

This lab has already produced a few useful lessons.

### Windows line endings

When I copied the Git repository from Windows to CachyOS, Git initially showed thousands of changed lines.

Nothing had actually changed.

It was just CRLF vs LF.

Running:

```bash
git diff --ignore-space-at-eol --stat
```

showed no real content differences.

### SOPS validation

My first GitHub Actions validation also tried to validate encrypted SOPS manifests as normal Kubernetes YAML.

That obviously did not work.

The workflow now skips `*.sops.yaml` files during kubeconform validation and checks them separately.

### GRUB after the SSD migration

The migrated filesystem was perfectly fine, but GRUB still had the old `/boot` UUID in its EFI config.

That was enough to drop the machine to a GRUB prompt even though all the data was there.

A nice reminder that “the files copied successfully” does not always mean “the system will boot.” 😄
