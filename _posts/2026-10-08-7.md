# Building My Two-Site K3s Homelab — *GitOps, Tailscale & Monitoring*

Over the last few days I’ve been building a small Kubernetes homelab.

The idea was simple: I wanted something small enough that I can understand every part of it, but still realistic enough to learn things I can actually use elsewhere.

I ended up with **two separate K3s clusters**:

- one at home on a **Radxa X4**
- one on an ARM cloud VM

They are connected with **Tailscale**, managed through **Flux GitOps**, and monitored with **Zabbix and Grafana**.

The lab is still very much a work in progress, but the core setup is finally stable enough that I thought it was worth writing down.

**Updated 24 October 2026:** both clusters now have Kubernetes monitoring, and the OCI applications have daily encrypted backups with verified copies in Cloudflare R2. Public SSH is closed at the host and cloud network layers. The remaining work includes a full recovery exercise and monitoring that can alert when OCI itself is unavailable.

## Why Two Clusters?

At first I did think about joining both machines into one Kubernetes cluster over Tailscale.

It can be done, but in my case it did not really make sense.

The control plane, and especially **etcd**, does not gain anything from sitting across a WAN link. It just adds latency and gives me one more thing to break.

So I kept the two clusters independent:

```text
Home cluster
  └── independent etcd

Cloud cluster
  └── independent etcd
```

If the home internet disappears, the Radxa can still keep doing its thing locally.

If the Radxa dies, the cloud cluster keeps running.

That separation also makes the cloud side useful for monitoring and the planned home-to-cloud backup path. OCI application backups now have their own off-node copy in Cloudflare R2.

## GitOps with Flux

Both clusters are managed with **Flux**.

The repository is split so each cluster only reconciles its own path:

```text
clusters/
├── home-cluster/
│   ├── flux-system/
│   └── infrastructure/
│
└── cloud-cluster/
    ├── flux-system/
    ├── infrastructure/
    └── monitoring/
        ├── grafana/
        └── zabbix/
```

The basic flow is:

```text
Git change
   |
   v
GitHub
   |
   v
Flux
   |
   v
Kubernetes
```

So if I change a manifest and push it, Flux picks it up and applies it to the right cluster.

I also added GitHub Actions validation so obvious YAML and manifest problems are caught before they get anywhere near the clusters.

## Secrets with SOPS + age

Plaintext secrets in Git were a no-go from the start.

For this I use:

- **SOPS**
- **age**

Each cluster has its own age key pair.

Encrypted files can live safely in the repository while the private keys stay outside Git.

Examples include:

- DNS provider API tokens
- Grafana admin credentials
- PostgreSQL credentials

Typical encrypted files look like:

```text
dns-api-token.sops.yaml
admin-secret.sops.yaml
postgres-access.sops.yaml
```

Flux decrypts them inside the cluster during reconciliation.

## Monitoring with Zabbix and Grafana

Monitoring runs in the cloud cluster, and that was very deliberate.

If Zabbix and Grafana only lived on the Radxa, they would vanish at exactly the same time as the thing I was trying to monitor.

Instead:

```text
home node
   |
   | Tailscale
   v
Zabbix
   |
   v
Grafana
```

The first layer monitors both hosts: CPU, memory, filesystems, network traffic, uptime and agent health. Grafana uses Zabbix as its data source so both sites can be viewed together.

### Progress update — 24 October 2026

That now extends into Kubernetes on **both clusters**. Each cluster runs kube-state-metrics, with Zabbix discovering pod health, restart counts, deployment replicas, node capacity and control-plane metrics. Kubelet collection also supplies measured pod CPU usage.

The home cluster needed a different collection path. The two sites have separate pod networks, so connecting to a discovered home Pod IP from the cloud is not a useful assumption. Zabbix now reads the named kube-state-metrics service through the authenticated Kubernetes API service proxy over Tailscale. It uses a dedicated read-only service account and trusts the home cluster CA for certificate verification.

Another K3s detail: the scheduler and controller-manager metrics are available through the authenticated API metrics endpoint. Their standalone ports remain bound to loopback. CPU and memory values from that combined endpoint describe the shared K3s process, which matters when interpreting a dashboard.

There are now **ten Grafana dashboards**: the infrastructure overview, the Linux server view, storage and network views, plus overview/control-plane/workload views for each cluster. I fixed the Linux dashboard's host, disk, filesystem and network filters, corrected the network units, and checked the Kubernetes queries against working Zabbix items. The workload views distinguish configured requests and limits from measured CPU usage.

I also found a notification trap: several Discord webhook parameters still contained fixed test values. Those have been restored to event macros so event IDs, severity and recovery status come from the actual event. One clearly labelled webhook test returned `OK`; earlier delivery records also show real host problem and recovery notifications. Warning-and-above delivery remains enabled.

The dashboard exports, restoration instructions and the credential-free Discord repair record are saved alongside the GitOps work. They are recovery copies: exporting a dashboard does not make its live settings automatically managed by Flux. The next reliability work is collection-failure alerts, service checks, backup freshness and a tested restore path.

## Daily Encrypted Backups and Cloudflare R2

The next gap was application data. Both clusters already take compressed etcd snapshots roughly every six hours, but those snapshots do not contain the files inside application PVCs. Recreating a Deployment from Git does not recover its database.

OCI now runs a daily application backup at **02:30–02:35 Perth time**, using a systemd timer on the host. The backup includes:

- a PostgreSQL 18 custom-format dump for Vikunja
- a PostgreSQL 16 custom-format dump for Zabbix
- Vikunja attachments and other files, excluding its transient upload directory
- checksums, a file inventory, version information and a restore-check report

The database archives are restored into disposable PostgreSQL pods before a successful backup is published. Those test instances have TCP listeners disabled and use temporary data volumes; they are removed afterward. The latest setup test recovered Vikunja's 53 tasks and 11 projects, and Zabbix's host, item and trigger records.

The resulting bundle is encrypted with **age** using the existing OCI recovery recipient. The private recovery key stays separate from the backup host and object storage. Recovering the archives will require both access to the stored objects and the original age identity.

### One backup per day, two retention windows

There are **14 successful local generations** on OCI and a **30-day expiration rule** for the backup prefix in a private Cloudflare R2 Standard bucket.

After a successful daily backup, `rclone` uploads the encrypted archive and its SHA-256 file. OCI then reads the entire encrypted object back from R2 and compares its SHA-256 with the local archive. An upload is recorded as verified only after both the archive and checksum file pass.

An hourly timer retries the latest unverified upload. It does **not** create another backup each hour, and it skips an already verified generation. The two archives initially visible in R2 came from setup testing: one existing archive tested the upload, and a fresh one exercised the complete pipeline.

The early archives were around 67–69 MB. At 100–150 MB each, thirty daily copies would occupy roughly 3–4.5 GB, before allowing for growth or other stored objects. Email and Discord notification destinations are set up for Cloudflare storage-usage alerts. The warning thresholds we chose are **7.5 billion bytes** and **8.5 billion bytes**, corresponding to 75% and 85% of a 10 GB storage allowance. These are usage warnings, not spending caps; current allowances are documented in [R2 pricing](https://developers.cloudflare.com/r2/pricing/).

S3 credentials were saved in Bitwarden and entered directly into a root-only configuration on OCI, with object access scoped to the backup bucket. No credentials were pasted into Git. The only new packages required on OCI were `age` and `rclone`, along with any package-manager dependencies.

The management workstation is deliberately absent from the scheduled path. It is not always online, so backup generation, upload, retries and readback verification all run on OCI.

### What the checks establish

The full backup-to-R2 pipeline and isolated SQL restores passed. A full rebuilt-cluster/application recovery exercise and an age decryption round-trip are still pending. Comparing encrypted bytes proves the remote copy matches the local archive; it does not prove that the recovery identity is accessible during a disaster.

The database and attachment captures are also live, rather than one atomic application snapshot. A restore may need attachment reconciliation if uploads or deletions occurred during capture. For a strict recovery checkpoint, application writes need to be quiesced first.

Grafana's database/plugins and cross-site copies of cluster snapshots and matching server tokens are still separate work. The daily application backup does not yet cover every piece of state needed to rebuild either site.

The host scripts, systemd units and recovery runbook are versioned alongside the homelab configuration. They are installed on the host separately from Flux, so a node rebuild must restore those units too.

## Closing Public SSH

A discovery-agent rescan spotted public IPs connected to port 22. That prompted a closer look at the authentication records before treating an established TCP connection as a logged-in session.

The two flagged connections had **timed out before authentication**. Other entries said `authenticating user root` and `[preauth]`; those describe attempts, not successful root logins. The successful-login query returned no `Accepted` entries for the reviewed day's regular OpenSSH journal. Legitimate Tailscale SSH sessions are handled separately by `tailscaled`.

There was still a real exposure to fix: OpenSSH was reachable publicly, even though password and keyboard-interactive authentication were already disabled.

I closed it at two layers:

1. A dedicated persistent nftables guard blocks host TCP/22 outside Tailscale and loopback, covering IPv4 and IPv6. It leaves the existing Kubernetes/Tailscale rules and other ports to their normal firewall processing.
2. The OCI subnet security-list rule allowing TCP/22 from anywhere was removed. Both attached NSGs were reviewed individually: they had the same display name but different IDs, and both contained only outbound rules. ICMP and outbound access were preserved.

A five-minute automatic rollback was armed for the host change. It was cancelled only after a fresh independent Tailscale login succeeded and a public connection test changed from an SSH banner to a timeout. Kubernetes remained Ready and private application HTTPS stayed healthy. Rule reload and boot enablement were checked; a reboot and out-of-band console recovery exercise have not been performed.

The cloud-rule review was done through the OCI console. Because the host firewall already blocked public SSH, a failed public probe alone could not prove that the cloud ingress rule had also been removed.

The emergency recovery notes now account for both layers: removing the host guard alone will not reopen public SSH when the OCI ingress allowance is absent. A working tailnet session or the separate OCI console recovery route is needed to diagnose access problems.

Vikunja self-registration is now disabled through GitOps as well. Existing-account login remains available; per-account two-factor enrollment is still an owner task.

### What the discovery scan taught me

The rescan correctly found the new timer, script and Flux revision, but some details needed interpretation:

- A 24-hour error count still included the R2 setup failures after the upload fix was in place. Current service status and the last verified archive were better evidence of the present state.
- Temporary restore-test pods generated readiness warnings during startup and cleanup. Those events were not production database outages.
- The scanner could not resolve the uploader's shell variables, so it labelled the R2 destination as undetermined. It also missed the age encryption stage.

A credential-free dependency/backup description would make that tooling more useful. Collecting the complete rclone credential file would be the wrong way to fill the discovery gap.

## Swapping the Radxa SSD

One of the more interesting side jobs was replacing the Radxa SSD.

Originally I used a **1 TB Crucial NVMe**.

That was complete overkill.

The Debian + K3s setup was barely using any of that space, so I decided to move it to a **512 GB NVMe** and put the 1 TB drive to better use in my main PC.

Because the destination disk was smaller than the source, I did not want to do a raw block clone and hope for the best.

Instead I recreated the disk layout manually:

```text
EFI
/boot
LVM
├── root
├── k3s
└── backup
```

Then I copied the filesystems with `rsync`.

The actual data migration was the easy part.

The fun started on the first boot. 😄

The Radxa dropped straight into:

```text
grub>
```

GRUB itself was there, but the EFI-side GRUB config was still pointing at the old `/boot` UUID.

Manually pointing GRUB at the correct partition was enough to get Debian booting again:

```text
set root=(hd0,gpt2)
set prefix=(hd0,gpt2)/grub
insmod normal
normal
```

Once the system was up, I corrected the EFI GRUB config so it searched for the new `/boot` UUID.

After that, normal boot was back.

K3s came up, the node returned to `Ready`, and all the workloads were still there.

The old 1 TB SSD was then wiped and reformatted as Btrfs for reuse.

That little detour probably deserves its own post at some point because migrating Linux + LVM + K3s to a smaller disk turned out to be more interesting than expected.

## Things That Went Wrong

This lab has already produced a few useful lessons.

### Windows line endings

When I copied the Git repository from Windows to CachyOS, Git initially showed thousands of changed lines.

Nothing had actually changed.

It was just CRLF vs LF.

Running:

```bash
git diff --ignore-space-at-eol --stat
```

showed there were no real content changes.

### SOPS validation

My first GitHub Actions validation also tried to validate encrypted SOPS manifests as normal Kubernetes YAML.

That obviously did not work.

The workflow now skips `*.sops.yaml` files during kubeconform validation and checks them separately.

### Two backup-tool surprises

Vikunja's container image did not include the usual `cat` utility, and its native dump command initialized the file handler by trying to clean the temporary upload directory. The scheduled files backup therefore uses a temporary helper with the files PVC mounted read-only, alongside the PostgreSQL custom dumps.

The Ubuntu-packaged rclone also returned HTTP 501 from its optional post-upload HEAD check even when the object had been uploaded. Retries eventually succeeded, but left misleading errors in the journal. Using `--s3-no-head` on uploads removed that compatibility problem; the complete encrypted-byte SHA-256 readback remains the integrity check.

### The moving CI runner

The blog deployment itself broke when `ubuntu-latest` moved to Ubuntu 26.04 and the runner lacked a prebuilt Ruby 3.3.9. Pinning the workflow to Ubuntu 24.04 restored the build and Pages deployment. Runner upgrades now need an explicit compatibility check against the pinned Ruby version.

### GRUB after the SSD migration

The migrated filesystem was fine, but GRUB was still looking for the old `/boot` UUID.

That was enough to drop the machine to a GRUB prompt even though all the data was sitting there perfectly intact.

A good reminder that "the copy finished successfully" and "the machine will boot" are two very different things. 😄

## What’s Next?

The lab is working, but it is nowhere near finished.

Kubernetes monitoring, daily encrypted application backups, verified R2 copies and the SSH exposure cleanup are working. The next reliability work is:

1. run an isolated end-to-end recovery exercise, including decryption, application login and attachment persistence
2. preserve independently accessible recovery keys, server tokens and cluster snapshots, then implement the designed home → cloud transfer
3. add backup-failure/freshness, service uptime, certificate and stale-collection alerts
4. add an independent watchdog so an OCI or Zabbix outage can still produce a notification
5. review OCI boot/block-volume backups and targeted Flux failure notifications
6. finish account 2FA enrollment and choose the first useful home application

A small scheduled Cloudflare Worker is the leading watchdog idea: it could check an OCI heartbeat and whether fresh encrypted backups reach R2. That Worker and the OCI volume-backup review are still plans, not deployed additions.

The current shortlist starts with a small **Homepage** portal and **Paperless-ngx**, after verifying the backup and restore path. **Mealie** is appealing for household planning; **Jellyfin** would make use of the home node's Intel hardware if a media library becomes the priority. **Home Assistant** is another route when there are devices and routines worth automating.

Photos would be a larger project. **Immich** is on the list, but memory, storage growth and recovery need a deliberate decision before it joins the smaller services. These are workload ideas, not applications already deployed.

I’m trying not to install everything just because I can.

The point is to add things when they either teach me something useful or solve an actual problem.

## Final Thoughts

The most useful part of this project so far has not really been getting Kubernetes running.

That part is the easy bit.

The interesting part is everything around it:

- managing two independent environments
- keeping secrets out of Git
- monitoring one site from another
- restoring database dumps before trusting a backup
- checking off-node copies rather than assuming an upload succeeded
- closing public management access without losing private access
- recovering when a bootloader points at the wrong disk
- keeping the whole thing reproducible

The lab is still growing, so I’ll probably split some of the more detailed pieces into their own posts later.

For now, the foundation is there.

And more importantly:

```text
kubectl get nodes
```

is green. 😄
